# Glossary

Core concepts and all 24 smell names. The 61 transformation names have their own alphabetic index in [SKILL.md](SKILL.md); mechanics live in the linked chapters. Chapter numbers below refer to that index.

- **Alternative Classes with Different Interfaces** — Equivalent capabilities with incompatible protocols. (Ch 3)
- **Assertion** — An executable required programmer invariant. (Ch 10)
- **Bad smell** — A structural signal warranting investigation. (Ch 3)
- **Branch By Abstraction** — Gradual implementation replacement behind a common interface. (Ch 2)
- **Command object** — An operation represented through an object and execution method. (Ch 11)
- **Command-query separation** — Separating information retrieval from observable updates. (Ch 11)
- **Comments** — Prose compensating for unclear code; rationale can remain useful. (Ch 3)
- **Comprehension refactoring** — Store discovered understanding in code names and structure. (Ch 2)
- **Continuous Integration** — Frequent integration of changes into a shared mainline. (Ch 2)
- **Data Class** — A data holder whose clients may own misplaced behavior. (Ch 3)
- **Data Clumps** — Meaningful groups recurring across fields and parameters. (Ch 3)
- **Derived variable** — Stored information calculable from other authoritative data. (Ch 9)
- **Design Stamina Hypothesis** — The hypothesis that good design sustains delivery speed. (Ch 2)
- **Divergent Change** — One module changes for several unrelated reasons. (Ch 3)
- **Duplicated Code** — Repeated knowledge requiring coordinated maintenance. (Ch 3)
- **Encapsulation** — A boundary hiding representation and controlling relevant updates. (Ch 7)
- **Feature Envy** — Behavior strongly dependent on another module's data. (Ch 3)
- **Fixture** — Data and resources establishing a test's initial state. (Ch 4)
- **Flag argument** — A caller-supplied choice of operation, often a literal. (Ch 11)
- **Global Data** — Broadly accessible data with difficult-to-track writers. (Ch 3)
- **Guard clause** — An early exit isolating an exceptional case. (Ch 10)
- **Insider Trading** — Excessive exchange of module-internal knowledge. (Ch 3)
- **Intermediate data** — A representation passed between distinct processing phases. (Ch 1, 6)
- **Large Class** — A class whose groups suggest multiple responsibilities. (Ch 3)
- **Lazy Element** — An element whose structure adds insufficient value. (Ch 3)
- **Litter-Pickup Refactoring** — Incremental cleanup encountered during ordinary work. (Ch 2)
- **Long Function** — A function whose mechanics obscure intention. (Ch 3)
- **Long Parameter List** — A call burdened by poorly organized inputs. (Ch 3)
- **Loops** — A prompt to consider pipelines or separated traversals. (Ch 3, 8)
- **Message Chains** — Navigation coupling clients to object relationships. (Ch 3)
- **Middle Man** — Forwarding whose cost exceeds its useful isolation. (Ch 3)
- **Mutable Data** — Changeable state invalidating assumptions elsewhere. (Ch 3)
- **Mysterious Name** — A name that conceals or misstates intent. (Ch 3)
- **Null Object** — A Special Case for missing data. (Ch 10)
- **Observable behavior** — Behavior preserved at the chosen system boundary. (Ch 2)
- **Parallel change / expand-contract** — Introduce, migrate, then retire compatible representations. (Ch 2)
- **Pipeline** — Collection operations expressing selection, transformation, and aggregation. (Ch 8)
- **Polymorphism** — Common operations dispatching to variant-specific behavior. (Ch 1, 10, 12)
- **Preparatory refactoring** — Restructuring that simplifies an imminent functional change. (Ch 2)
- **Primitive Obsession** — Domain concepts kept primitive while their rules scatter. (Ch 3)
- **Published interface** — An interface serving independently controlled clients. (Ch 2)
- **Refactoring** — Behavior-preserving transformations improving understanding and modification cost. (Ch 2)
- **Reference object** — A shared entity identity with shared update visibility. (Ch 9)
- **Referential transparency** — Replacing an expression with its value preserves behavior. (Ch 11)
- **Refused Bequest** — Unneeded inherited features; refusing the interface is worse. (Ch 3)
- **Repeated Switches** — Category dispatch duplicated across operations. (Ch 3)
- **Repository** — Access to canonical entity instances by identity. (Ch 9)
- **Rule of Three** — A heuristic to reconsider duplication on its third occurrence. (Ch 2)
- **Self-testing code** — Code with automated, self-checking behavior tests. (Ch 4)
- **Shotgun Surgery** — One change requiring edits across many modules. (Ch 3)
- **Special Case** — Common exceptional-value behavior in an object or record. (Ch 10)
- **Speculative Generality** — Unused flexibility complicating current work. (Ch 3)
- **Temporary Field** — Object state relevant only in certain circumstances. (Ch 3)
- **Test-Driven Development** — Short failing-test, implementation, and refactoring cycles. (Ch 4)
- **The Two Hats** — Distinguishing functional changes from structural changes. (Ch 2)
- **Type-instance homonym** — Confusing a category/description with a particular instance. (Ch 12)
- **Value object** — Immutable contents-based value, replaced on change. (Ch 9)
- **Yagni** — Design for understood needs; defer speculative complexity. (Ch 2)

Common aliases: **Extract Method** → Extract Function; **Inline Method** → Inline Function; **Rename Function / Rename Method / Change Signature** → Change Function Declaration; **Introduce Null Object** → Introduce Special Case; **Replace Method with Method Object** → Replace Function with Command. These support lookup; this skill retains second-edition entry names.
