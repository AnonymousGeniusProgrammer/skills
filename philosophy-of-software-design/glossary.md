# Glossary

First-edition terms; see [chapter index](SKILL.md#chapter-index).

- **Abstraction** — A view retaining essential information and omitting unimportant detail. (Ch 4)
- **Change amplification** — One conceptual change requires modifications in many places. (Ch 2)
- **Classitis** — Excessive subdivision into classes that hide little complexity. (Ch 4)
- **Cognitive load** — Information a developer must hold or acquire to perform a task. (Ch 2)
- **Comment Repeats Code** — A comment supplies no meaningful information beyond the adjacent code. (Ch 13)
- **Complexity** — Structural difficulty in understanding and modifying a software system. (Ch 2)
- **Composition** — Building on another component's operations rather than inheriting its implementation. (Ch 19)
- **Conjoined Methods** — Separate methods whose implementations must be read together to understand either. (Ch 9)
- **Consistency** — Similar concepts use similar forms, and different concepts remain distinguishable. (Ch 17)
- **Context object** — Per-instance shared state that can reduce pass-through arguments. (Ch 7)
- **Critical path** — In this chapter's optimization technique, the minimal work for the selected common operation. (Ch 20)
- **Cross-module comment** — Documentation of a decision or dependency spanning module boundaries. (Ch 13, 16)
- **Decorator** — An object that adds behavior around another while retaining much of its interface. (Ch 7)
- **Deep module** — Substantial functionality behind a relatively simple interface. (Ch 4)
- **Define errors out of existence** — Broaden an operation's useful normal semantics so a former error case needs no exceptional handling. (Ch 10)
- **Dependency** — A relationship that prevents understanding or changing one piece of code in isolation. (Ch 2)
- **Design it twice** — Compare meaningfully different design alternatives before choosing. (Ch 11)
- **Design pattern** — A recognized solution to a recurring kind of problem, useful when it fits. (Ch 19)
- **Error promotion** — Reusing recovery for a broader failure to handle a narrower one. (Ch 10)
- **Exception** — Any unusual condition altering control flow, including statuses and sentinel results. (Ch 10)
- **Exception aggregation** — Handling several errors through one appropriate common response or recovery mechanism. (Ch 10)
- **Exception masking** — Recovering at a lower layer so a caller need not handle the condition. (Ch 10)
- **False abstraction** — A simplified view that omits information its users actually need. (Ch 4, 6)
- **Fence** — A history marker separating groups of undoable actions in the editor example. (Ch 9)
- **Fundamental fix** — A structural performance improvement that avoids expensive work through a different approach. (Ch 20)
- **General-purpose module** — A module expressed in concepts usable beyond one specific caller or feature. (Ch 6)
- **Hard to Describe** — Difficulty expressing a complete, simple contract, suggesting an awkward abstraction. (Ch 15)
- **Hard to Pick Name** — Naming difficulty that may reveal an unclear purpose or representation. (Ch 14)
- **Implementation comment** — An explanation of internal purpose, strategy, or rationale for maintainers. (Ch 13)
- **Implementation Documentation Contaminates Interface** — Caller documentation includes unnecessary mechanism details. (Ch 13)
- **Implementation inheritance** — Reusing a parent's method implementations, with possible subclass overrides. (Ch 19)
- **Information hiding** — Confining design knowledge within its owning module. (Ch 5)
- **Information leakage** — The same design decision is reflected in several modules. (Ch 5)
- **Interface** — All formal and informal knowledge necessary to use a module. (Ch 4)
- **Interface inheritance** — Sharing operation signatures and contracts across distinct implementations. (Ch 19)
- **Invariant** — A property maintained as true for a representation or structure. (Ch 13, 17)
- **Microbenchmark** — A focused measurement of a small operation's cost. (Ch 20)
- **Module** — A unit with an interface and an implementation, at function, class, subsystem, or service scale. (Ch 4)
- **Nonobvious Code** — Code whose meaning or behavior resists a quick, accurate reading. (Ch 18)
- **Obscurity** — Necessary information that is not apparent or discoverable. (Ch 2)
- **Overexposure** — Common usage requires learning rarely needed features. (Ch 5)
- **Pass-through method** — A method doing little beyond forwarding to another with a similar signature. (Ch 7)
- **Pass-through variable** — A value propagated through methods that do not use it. (Ch 7)
- **Pull complexity downwards** — Absorb related complexity within an abstraction to simplify its callers. (Ch 8)
- **Red flag** — A symptom suggesting a design deserves examination and alternatives. (Ch 1)
- **Repetition** — Recurring nontrivial code that may indicate a missing abstraction. (Ch 9)
- **Shallow module** — A module that hides little relative to its interface cost. (Ch 4)
- **Somewhat general-purpose** — Current functionality presented through a reusable interface that remains convenient now. (Ch 6)
- **Special-General Mixture** — A reusable mechanism also contains policy specific to one of its uses. (Ch 9)
- **Strategic programming** — Continuous investment in a structure that supports future changes. (Ch 3)
- **Tactical programming** — Prioritizing the next working change while deferring structural costs. (Ch 3)
- **Tactical tornado** — An extreme tactical programmer whose visible output leaves maintenance costs for others. (Ch 3)
- **Temporal decomposition** — Partitioning code by execution stage, risking duplicated knowledge across stages. (Ch 5)
- **Unknown unknowns** — Necessary information a developer does not know to seek. (Ch 2)
- **Vague Name** — An identifier compatible with too many meanings to guide use reliably. (Ch 14)
