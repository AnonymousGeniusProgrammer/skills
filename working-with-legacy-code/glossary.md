# Glossary

Alphabetical concept lookup. Named dependency-breaking procedures are indexed in the [catalog](chapters/ch25-dependency-breaking-techniques.md).

- **Bulleted method** — Long sequence of chunks whose local values may connect them despite visual separation. (Ch 22)
- **Characterization test** — Test that records observed existing behavior to detect changes, without claiming that behavior is desirable. (Ch 13)
- **Command/Query Separation** — Separate state-changing operations from operations returning information where this clarifies testing and use. (Ch 10)
- **Compilation firewall** — Boundary that limits propagation of implementation changes into client recompilation. (Ch 7)
- **Construction blob** — Constructor work that creates and uses intertwined dependencies, obstructing substitution. (Ch 9)
- **Coupling count** — Number of values crossing an extracted method's input/output interface; instance-field accesses are excluded, not rendered harmless. (Ch 22)
- **Cover and Modify** — Establish preservation tests before changing the covered behavior. (Ch 2)
- **Decorator** — Wrapper usable through the wrapped object's interface, adding behavior while delegating. (Ch 6)
- **Edit and Pray** — Change code and rely on later checking without immediate preservation feedback. (Ch 2)
- **Effect sketch** — Graph of possible influence from changed values or operations to observable effects. (Ch 11)
- **Enabling point** — Place where a seam's alternative behavior is selected. (Ch 4)
- **Fake object** — Substitute used to make a test possible through controlled behavior or observations; the book uses the term broadly. (Ch 3)
- **Feature sketch** — Diagram of which methods and state a feature uses, helping identify responsibilities. (Ch 20)
- **Gleaning Dependencies** — Protect critical behavior with tests before extracting surrounding less-protected dependencies. (Ch 22)
- **Hidden dependency** — Collaborator acquired internally rather than supplied explicitly at the visible interface. (Ch 9–10)
- **Hyperaware Editing** — Deliberate awareness of each edit's behavioral intent supported by fast feedback. (Ch 23)
- **Interception point** — Location at which effects of a change can be observed by a test. (Ch 12)
- **Interface Segregation Principle** — Give clients interfaces focused on the operations they need. (Ch 20)
- **Lazy getter** — Accessor that creates and stores an object at first use; it changes initialization timing. (Ch 25)
- **Lean on the Compiler** — Change a declaration and use resulting errors to locate required edits, respecting compiler blind spots. (Ch 23)
- **Legacy Code Change Algorithm** — Identify change points; find test points; break dependencies; write tests; make changes and refactor. (Ch 2)
- **Legacy Code Dilemma** — Tests are needed to change code, but code may need changing to install tests. (Ch 2)
- **Legacy code** — Code without tests, in Feathers's working definition. (Introduction, Ch 1–2)
- **Link seam** — Substitution selected through build, linking, or loading arrangements. (Ch 4)
- **Liskov Substitution Principle** — Subtype behavior must remain compatible with the expectations of clients using the base abstraction. (Ch 8)
- **Method object** — Object embodying one method's work, with its inputs and working state available for further decomposition. (Ch 22, 25)
- **Mock object** — Test collaborator that checks expected interactions; distinguish its verification role from merely returning canned data. (Ch 3, 5)
- **Naked CRC** — Informal object/collaboration exploration using blank cards and spatial relationships rather than fully written responsibility lists. (Ch 17)
- **Normalized hierarchy** — Hierarchy in which a method has at most one implementation along a path through inheritance. (Ch 8)
- **Null Object Pattern** — Object providing legitimate neutral behavior in place of absence; not equivalent to passing null. (Ch 9)
- **Object seam** — Substitution through object identity and polymorphic calls. (Ch 4)
- **Onion parameter** — Parameter that exists mainly to supply another object, producing nested setup dependencies. (Ch 9)
- **Open/Closed Principle** — Design supports extension with limited modification of existing behavior. (Ch 21)
- **Orthogonality** — Behaviors can change independently, with fewer coordinated edit locations. (Ch 21)
- **Pass Null** — Narrow test-setup probe for an unused parameter on a verified path, subject to language constraints. (Ch 9)
- **Pinch point** — Point where relevant effects for a selected change set concentrate, permitting economical coverage. (Ch 12)
- **Preprocessing seam** — Substitution selected while transforming source before compilation. (Ch 4)
- **Preserve Signatures** — Retain method argument/result details during mechanical moves to reduce transcription and conversion errors. (Ch 23)
- **Programming by Difference** — Add behavior through a subclass, then integrate common behavior by refactoring. (Ch 8)
- **Scratch refactoring** — Disposable restructuring used to learn about code before making a production change. (Ch 16)
- **Seam** — Place where behavior can be substituted without repeatedly editing the use site. (Ch 4)
- **Sensing** — Observing values, state changes, or interactions during execution. (Ch 3)
- **Sensing variable** — Temporary observable state added to inspect an otherwise hard-to-see intermediate effect. (Ch 22)
- **Separation** — Removing an execution dependency so a unit can run in a useful harness. (Ch 3)
- **Single-Goal Editing** — Complete and check one immediate transformation before beginning another. (Ch 23)
- **Single Responsibility Principle** — A class has a coherent purpose and reason to change. (Ch 20)
- **Snarled method** — Large method dominated by deeply nested control flow. (Ch 22)
- **Software vise** — Tests hold selected behavior steady during change. (Ch 2)
- **Static cling** — Trouble substituting a dependency expressed through static calls. (Ch 25)
- **Targeted testing** — Select cases for specific change risks, including whether extracted logic remains connected correctly. (Ch 13)
- **Test harness** — Supporting code and tools that construct, exercise, observe, and check the unit under test. (Ch 5)
