# Glossary

References: [chapter index](SKILL.md#chapter-index).

- **Abstract Core** — Fundamental domain abstractions expressing major component interactions. (Ch 15)
- **Account** — Collection of Entries with a resulting balance. (Ch 11)
- **Accrual** — Recognition of income or expense when incurred, independently of payment. (Ch 9, 11)
- **Aggregate** — Related objects treated as a unit for changes and consistency. (Ch 6)
- **Aggregate root** — Entity controlling an Aggregate's external access and invariants. (Ch 6)
- **Analysis pattern** — Reusable modeling knowledge with alternatives and implementation consequences. (Ch 11)
- **Anticorruption Layer** — Translation protecting a local model from foreign semantics. (Ch 14)
- **Assertion** — Explicit precondition, postcondition, or invariant. (Ch 10)
- **Association** — Domain relationship represented through interaction or reference. (Ch 5)
- **Bounded Context** — Explicit scope in which a particular model remains unified. (Ch 14)
- **Breakthrough** — Substantial insight enabling a deeper model. (Ch 8)
- **Closure of Operations** — Results remaining in the input conceptual type. (Ch 10)
- **Cohesive Mechanism** — Encapsulated computation resolving problems posed by expressive models. (Ch 15)
- **Composite** — Uniform behavioral abstraction for a part-whole hierarchy. (Ch 12)
- **Conceptual Contours** — Meaningful divisions accommodating different reasons for change. (Ch 10)
- **Conformist** — Downstream adoption of an upstream model without shared stewardship. (Ch 14)
- **Context Map** — Current models, boundaries, sharing, translation, and team relationships. (Ch 14)
- **Continuous Integration** — Frequent reconciliation of both model concepts and implementation. (Ch 14)
- **Core Domain** — Model concepts distinctive and central to the application's purpose. (Ch 15)
- **Customer/Supplier Development Teams** — Negotiated upstream/downstream commitments and acceptance tests. (Ch 14)
- **Declarative style** — Composable domain expressions with encapsulated execution. (Ch 10)
- **Deep model** — Model expressing useful underlying domain relationships. (Ch 8-13)
- **Domain** — Subject area to which users apply the software. (Ch 1)
- **Domain Vision Statement** — Brief account of the core model's distinctive value. (Ch 15)
- **Entity** — Object defined by identity and continuity rather than attributes alone. (Ch 5)
- **Entry** — Recorded change contributing to an Account's balance and history. (Ch 11)
- **Evolving Order** — Revisable organizing structure developed through application experience. (Ch 16)
- **Factory** — Encapsulation of complex creation or reconstitution. (Ch 6)
- **False cognate** — Shared term concealing incompatible meanings. (Ch 14)
- **Flyweight** — Shared representation of repeated equivalent values; technical here. (Ch 5, 12)
- **Generic Subdomain** — Cohesive domain support without project-specific specialization. (Ch 15)
- **Hands-On Modeler** — Modeler participating in implementation and its feedback. (Ch 3)
- **Highlighted Core** — Visible core identification through marking or concise documentation. (Ch 15)
- **Intention-Revealing Interface** — Purpose understandable without implementation knowledge. (Ch 10)
- **Invariant** — Condition required at the model's relevant consistency boundary. (Ch 6, 10)
- **Knowledge Crunching** — Iterative synthesis of expertise, modeling, scenarios, and implementation. (Ch 1)
- **Knowledge Level** — Domain objects configuring other domain objects. (Ch 16)
- **Layered Architecture** — Separation of presentation, application, domain, and infrastructure concerns. (Ch 4)
- **Model** — Selective abstraction useful for understanding and solving domain problems. (Ch 1-3)
- **Model-Driven Design** — Tight correspondence and feedback between model and implementation. (Ch 3)
- **Module** — Cohesive conceptual partition with limited dependencies. (Ch 5)
- **Open Host Service** — Coherent service protocol available to multiple integrating consumers. (Ch 14)
- **Pluggable Component Framework** — Shared contracts for interchangeable domain implementations. (Ch 16)
- **Posting Rule** — Rule deriving postings from relevant input-account Entries. (Ch 11)
- **Published Language** — Documented common model used for interchange. (Ch 14)
- **Reconstitution** — Restoring an existing object's identity and state. (Ch 6)
- **Repository** — Model-oriented access to existing objects. (Ch 6)
- **Responsibility Layers** — Domain strata with downward conceptual dependencies. (Ch 16)
- **Segregated Core** — Core concepts explicitly separated from supporting model and code. (Ch 15)
- **Separate Ways** — Independent contexts with no meaningful domain integration. (Ch 14)
- **Service** — Meaningful operation without a natural home in an Entity or Value Object. (Ch 5)
- **Shared Kernel** — Limited model and implementation subset under joint stewardship. (Ch 14)
- **Side-Effect-Free Function** — Operation returning a result without observable state change. (Ch 10)
- **Smart UI** — Application style placing behavior with UI and direct data access. (Ch 4)
- **Specification** — Explicit criterion for candidate satisfaction. (Ch 9)
- **Standalone Class** — Concept understandable with few external conceptual dependencies. (Ch 10)
- **Strategy/Policy** — Explicit interchangeable rule governing a process. (Ch 12)
- **Subsumption** — In Evans's example, stronger criterion implies weaker criterion. (Ch 10)
- **Supple design** — Predictable design supporting combination and change. (Ch 10)
- **System Metaphor** — Concrete analogy guiding the system's shared organizing view. (Ch 16)
- **Transaction, accounting** — Conserved value movement between Accounts; not database transaction. (Ch 11)
- **Ubiquitous Language** — Model-based language shared in conversation, design, and code within context. (Ch 2)
- **Value Object** — Descriptive object defined by its attributes, without conceptual identity. (Ch 5)
