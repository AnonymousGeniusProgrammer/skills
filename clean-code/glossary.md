# Glossary

Definitions are synthesized from the book. Chapter references identify the primary discussion; use the chapter index in [SKILL.md](SKILL.md) to navigate.

- **Abstraction level** — The degree of general policy versus implementation detail expressed by an operation. (Ch 3, 17)
- **Active Record** — A record-like structure with persistence/navigation methods; the source distinguishes it from a domain object owning business behavior. (Ch 6)
- **Adapter** — Translates an interface a client needs to one another component provides. (Ch 8, 13)
- **ArgumentMarshaler** — The Args case study's type-specific argument consumer and value holder. (Ch 14)
- **Argument object** — A named concept grouping related inputs. (Ch 3)
- **Aspect** — A modular definition of behavior applied at selected execution points. (Ch 11)
- **Atomic operation** — An operation whose defined effect cannot be interleaved with competing access partway through. (Ch 13, App A)
- **Big Design Up Front (BDUF)** — Attempting complete design before implementation feedback, distinguished from useful initial design. (Ch 11)
- **Bound resource** — A resource with fixed capacity or quantity. (Ch 13)
- **Boy Scout Rule** — Improve the maintainability of the code you touch through small local changes. (Ch 1)
- **Build-Operate-Check** — Test structure separating setup, the action, and verification. (Ch 9)
- **CAS (Compare-and-Swap)** — Atomically replace a value only if it matches the expected prior value. (App A)
- **Client-based locking** — Clients protect a complete operation sequence with the required lock. (Ch 13, App A)
- **Code-sense** — Judgment for recognizing useful behavior-preserving transformations. (Ch 1)
- **Cohesion** — How closely a unit's state and behavior form one meaningful responsibility. (Ch 10)
- **Command Query Separation** — Distinguish operations that change state from operations that answer questions. (Ch 3)
- **Conceptual affinity** — Shared purpose that makes code elements useful to read together. (Ch 5)
- **Coupling** — Dependence on another unit's decisions or implementation details. (Ch 10)
- **Critical section** — Code requiring controlled concurrent access to preserve correctness. (Ch 13)
- **Cross-cutting concern** — A policy, such as persistence or transactions, intersecting multiple domain units. (Ch 11)
- **Data/Object Anti-Symmetry** — Procedures over data ease adding operations; polymorphic objects ease adding types. (Ch 6)
- **Data Transfer Object (DTO)** — A structured representation intended for transferring information. (Ch 6)
- **Dead code** — Code without required reachable behavior. (Ch 17)
- **Deadlock** — Participants wait for resources held by one another so none can progress. (Ch 13, App A)
- **Dependency Injection (DI)** — Supply an object's dependencies instead of having it resolve or construct them. (Ch 11)
- **Dependency Inversion Principle (DIP)** — Depend on abstractions instead of concrete implementation details. (Ch 10)
- **Domain-Specific Language (DSL)** — A vocabulary and structure for expressing a particular problem domain. (Ch 3, 9, 11)
- **DRY** — Keep one appropriate implementation of knowledge that must change together. (Ch 3, 12, 17)
- **Emergent design** — Structure developed through tests, implementation, and repeated refinement. (Ch 12)
- **Executor** — A mechanism responsible for scheduling submitted tasks. (App A)
- **F.I.R.S.T.** — Fast, Independent, Repeatable, Self-Validating, Timely tests. (Ch 9)
- **Factory** — Separates how an object is constructed from the consumer deciding when it is needed. (Ch 3, 11, 16)
- **Fake** — A substitute with sufficient behavior to support isolated scenarios. (Ch 8)
- **Feature envy** — Behavior relying heavily on another concept's information, suggesting a possible ownership move. (Ch 16, 17)
- **Flag argument** — A parameter selecting distinct behavior inside a function. (Ch 3)
- **Future** — A handle for a result produced by work that may still be running. (App A)
- **Hybrid** — A structure exposing internals while also claiming to encapsulate significant behavior. (Ch 6)
- **Intention-revealing name** — A name conveying why an entity exists and what it does. (Ch 2)
- **Inversion of Control (IoC)** — Move a secondary responsibility to a mechanism dedicated to it. (Ch 11)
- **Jiggling** — Test-time variation of scheduling to expose concurrency failures. (Ch 13)
- **Law of Demeter** — Limit knowledge of behavioral objects' internal navigation structure. (Ch 6)
- **Learning test** — An executable experiment recording a dependency behavior the application needs. (Ch 8)
- **Livelock** — Participants continue reacting or retrying without useful progress. (Ch 13)
- **Logical dependency** — An assumption about another component that is not expressed through its contract. (Ch 16, 17)
- **Magic value** — A literal whose significance is not apparent in context. (Ch 17)
- **Mental mapping** — Decoding arbitrary names or encodings into their actual meaning. (Ch 2)
- **Mutual exclusion** — Only one participant can use a protected resource at a time. (Ch 13)
- **Newspaper Metaphor** — Present a source file's main story before its supporting details. (Ch 5)
- **Niladic / monadic / dyadic / triadic** — Functions with zero / one / two / three arguments. (Ch 3)
- **One Switch** — Martin's heuristic centralizing a given type selection in object construction. (Ch 17)
- **Open-Closed Principle (OCP)** — Enable extension while keeping stable behavior closed to modification. (Ch 10)
- **Ordinal day** — A numeric day representation relative to an origin. (Ch 16)
- **Output argument** — A parameter mutated to convey a result. (Ch 3)
- **POJO** — Plain Old Java Object; used to describe behavior independent of invasive infrastructure. (Ch 11)
- **Seam** — A boundary at which an alternative implementation can be supplied. (Ch 8)
- **Selector argument** — A mode value choosing a workflow; it need not be Boolean. (Ch 17)
- **Separation of Main** — Startup constructs and wires dependencies, then supplies them to the application. (Ch 11)
- **Server-based locking** — The shared object owns the full protected operation. (Ch 13, App A)
- **Side effect** — An observable change a caller must understand, especially one hidden by the interface. (Ch 3)
- **Simple Design** — Ordered priorities: tests pass, no duplication, clear intent, minimal classes/methods. (Ch 12)
- **Single Responsibility Principle (SRP)** — One reason for a class or module to change. (Ch 10)
- **Special Case Pattern** — Encapsulate a defined alternative behind the ordinary interface. (Ch 7)
- **Starvation** — A participant is denied progress for an excessive or indefinite period. (Ch 13)
- **Stepdown Rule** — Read high-level operations followed by their next-level supporting steps. (Ch 3)
- **Successive refinement** — Improve a working draft through small verified changes. (Ch 14)
- **Template Method** — A shared algorithm skeleton with selected variable steps. (Ch 12)
- **Temporal coupling** — A dependency on operations occurring in a required order. (Ch 3, 15, 17)
- **Train wreck** — Chained navigation that may expose an internal object graph. (Ch 6)
